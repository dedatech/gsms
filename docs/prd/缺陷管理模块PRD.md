## 1. 文档概述

### 1.1 背景

缺陷是质量检查（Check）阶段的核心产出，需要独立的跟踪和管理流程。

### 1.2 目标

提供清晰的缺陷跟踪视图，支持测试→修复→验证的完整闭环。

### 1.3 范围

本PRD涵盖项目详情页中的缺陷管理功能，包括：

- 缺陷列表展示
- 缺陷创建与编辑
- 缺陷状态流转
- 缺陷修复验证

---

## 2. 产品定位

### 2.1 模块定位

**缺陷管理模块**是质量检查（Check）阶段的核心工具，负责：

- 记录测试发现的缺陷
- 跟踪缺陷修复进度
- 验证修复结果
- 缺陷 reopen 处理

### 2.2 用户角色

| 角色   | 职责              | 权限      |
| ---- | --------------- | ------- |
| 测试人员 | 创建缺陷、验证修复      | 创建+验证  |
| 开发人员 | 修复缺陷、更新状态      | 编辑+状态更新 |
| 项目经理 | 分配缺陷、查看整体进度   | 所有权限    |

## 3. 功能需求

### 3.1 缺陷列表

#### 功能描述

以列表/看板形式展示所有缺陷，支持筛选和搜索。

#### 功能列表

| 功能     | 描述                          | 优先级 |
| ------ | --------------------------- | --- |
| 缺陷列表   | 以表格形式展示所有缺陷              | P0  |
| 看板视图   | 按状态分列展示缺陷                | P1  |
| 状态筛选   | 按状态筛选缺陷（待处理/进行中/待验证/已关闭）| P1  |
| 严重程度筛选 | 按严重程度筛选（致命/严重/一般/轻微）       | P1  |
| 负责人筛选  | 按负责人筛选                      | P1  |
| 优先级筛选  | 按优先级筛选                      | P1  |
| 缺陷搜索   | 按标题关键词搜索                    | P1  |

#### 交互说明

- 顶部工具栏：筛选条件 + 搜索框 + 新建缺陷按钮
- 主体区域：缺陷列表/看板，支持拖拽更新状态
- 缺陷卡片显示：标题、严重程度、优先级、负责人、状态

### 3.2 缺陷管理

#### 功能描述

记录测试发现的缺陷，跟踪修复进度。

#### 功能列表

| 功能      | 描述            | 优先级 |
| ------- | ------------- | --- |
| 新建缺陷    | 快速记录发现的缺陷     | P0  |
| 编辑缺陷    | 修改缺陷信息        | P0  |
| 设置严重程度   | 致命/严重/一般/轻微   | P0  |
| 分配负责人   | 指定修复人员        | P0  |
| 记录复现步骤   | 详细描述问题复现过程    | P0  |
| 添加附件     | 上传截图、日志等附件    | P1  |
| 设置修复版本   | 标记缺陷修复所在版本    | P1  |
| 验证修复     | 测试人员确认缺陷已修复   | P0  |
| 重新打开     | 修复不通过时重新打开缺陷 | P0  |
| 关联需求/任务  | 缺陷关联到相关需求或任务 | P1  |

#### 交互说明

- 缺陷卡片用红色标签标识，区别于任务
- 严重程度用颜色区分：致命(红) / 严重(橙) / 一般(黄) / 轻微(蓝)
- 支持从任务执行模块快速创建缺陷
- 验证失败时，支持一键重新打开（reopen）

### 3.3 详情查看

#### 功能描述

点击缺陷卡片查看完整信息。

#### 功能列表

| 功能     | 描述          | 优先级 |
| ------ | ----------- | --- |
| 查看详情   | 显示缺陷完整信息    | P0  |
| 编辑信息   | 可编辑各字段内容    | P0  |
| 查看修复历史 | 显示修复和验证历史    | P1  |
| 查看附件   | 显示上传的截图等附件  | P1  |

## 5. 交互流程

### 5.1 新建缺陷流程

```
测试人员点击"新建缺陷"
    ↓
填写缺陷信息（标题、严重程度、复现步骤等）
    ↓
保存
    ↓
缺陷出现在"待处理"状态
    ↓
通知被分配的开发人员
```

### 5.2 缺陷修复流程

```
开发人员查看缺陷
    ↓
开始修复，状态更新为"进行中"
    ↓
修复完成，状态更新为"待验证"
    ↓
通知测试人员验证
```

### 5.3 验证与重开流程

```
测试人员验证缺陷修复
    ↓
    ├── 验证通过 → 状态更新为"已完成"
    │
    └── 验证失败 → 点击"重新打开"
            ↓
          状态重置为"待处理"
            ↓
          通知开发人员继续修复
```

## 6. 数据模型

### 6.1 缺陷字段（继承 Task，type=BUG）

| 字段             | 类型      | 必填  | 说明                         |
| ------------- | ------- | --- | -------------------------- |
| id             | Long    | ✅   | 缺陷唯一标识                     |

| type           | Enum    | ✅   | 固定为 BUG                      |
| priority       | Enum    | ✅   | 优先级（LOW/MEDIUM/HIGH）       |
| status         | Enum    | ✅   | 状态                         |
| severity      | Enum    | ✅   | 严重程度（缺陷特有字段）             |
| reproductionSteps | String | ❌   | 复现步骤（缺陷特有字段）             |
| attachments    | String  | ❌   | 附件列表（JSON格式，缺陷特有字段）       |
| fixVersion    | String  | ❌   | 修复版本（缺陷特有字段）             |
| assigneeId     | Long    | ❌   | 负责人ID（修复人）                |
| iterationId    | Long    | ❌   | 关联迭代ID                     |
| projectId     | Long    | ✅   | 所属项目ID                     |

## 7. 状态流转

### 7.1 状态枚举（与后端 TaskStatus 一致）

| 枚举值 | Code | 显示文本  | 说明     |
| ------ | ---- | ----- | ------ |
| TODO | 1 | 待处理   | 初始状态   |
| IN_PROGRESS | 2 | 进行中   | 正在修复   |
| TESTING | 4 | 待验证   | 等待测试验证 |
| DONE | 3 | 已完成   | 验证通过   |
| REOPENED | 5 | 重新打开  | 重新进入修复 |
| CLOSED | 6 | 已关闭   | 最终关闭   |

### 7.2 缺陷状态流转

```
┌──────────────────────────────────────────────┐
│  缺陷状态流转                                   │
│                                               │
│  [待处理] ──→ [进行中] ──→ [待验证] ──→ [已完成] │
│     ↑                                      │
│     └────────────────────────────────────┘        │
│              重新打开                            │
└──────────────────────────────────────────────┘

状态说明：
- 待处理(TODO)：已记录，待分配修复
- 进行中(IN_PROGRESS)：正在修复中
- 待验证(TESTING)：修复完成，等待测试验证
- 已完成(DONE)：验证通过，待关闭
- 重新打开(REOPENED)：验证失败，重新进入修复流程
- 已关闭(CLOSED)：正式关闭

特殊流转：
- 缺陷从「待验证」退回到「重新打开」时，自动流转到「待处理」
- 重新打开的缺陷需要再次经过完整修复流程
```

## 8. 非功能需求

### 8.1 性能需求

- 缺陷列表加载时间 < 1秒
- 状态更新响应时间 < 500ms

### 8.2 安全需求

- 只有项目成员可以查看缺陷
- 测试人员可创建和验证缺陷
- 开发人员可更新修复状态

### 8.3 兼容性需求

- 支持主流浏览器（Chrome、Firefox、Safari）
- 响应式设计，支持1920x1080及以上分辨率
